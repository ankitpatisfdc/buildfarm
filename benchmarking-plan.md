# Redis vs Valkey Benchmarking Plan for Buildfarm

## Executive Summary

This document outlines a comprehensive benchmarking strategy to compare Redis against Valkey using real-world workloads generated by Buildfarm. The plan focuses on testing actual usage patterns observed in Buildfarm's remote execution system to provide meaningful performance comparisons.

## 1. Background and Motivation

### Buildfarm's Redis Usage Patterns

Based on analysis of the Buildfarm codebase, Redis serves as the "backplane" - a critical shared communication layer supporting:

- **Queue Operations**: BalancedRedisQueue distributes build jobs across workers using multiple Redis lists with hashtags for load balancing
- **Metadata Storage**: Action cache, operation status, worker registration, and execution metadata
- **Content Addressable Storage (CAS)**: Blob location tracking and availability across distributed workers
- **Worker Coordination**: Pub/sub messaging for operation updates, worker heartbeats, and cluster coordination
- **Session Management**: Operation lifecycles, timeouts, and state transitions

### Valkey Positioning

Valkey (BSD-licensed Redis fork) offers:
- Enhanced I/O multithreading (reported 3x performance improvements)
- 20% memory efficiency gains in version 8.1
- Better multi-core utilization
- Open-source governance model
- Protocol compatibility with Redis

### 2.2 Workload Characterization

#### Core Buildfarm Workload Patterns

**Queue Operations (Primary Workload)**
```java
// Pattern observed in BalancedRedisQueue.java
- LPUSH/RPOP operations for job queuing
- Round-robin distribution across multiple queues using hashtags
- Blocking operations (BLPOP) with timeouts
- Queue size monitoring (LLEN)
- Dequeue management for fault tolerance
```

**Metadata Operations**
```java
// Pattern from ShardActionCache.java and operation management
- HSET/HGET for action results and operation metadata
- SETEX for time-based expiration (action cache, operation timeouts)
- SETNX for distributed locking
- Multi-key operations (MGET/MSET) for batch processing
```

**Worker Coordination**
```java
// Pattern from worker management and pub/sub
- PUBLISH/SUBSCRIBE for real-time worker updates
- SET with TTL for worker heartbeats and registration
- SADD/SREM for worker set management
- Hash operations for worker capabilities and status
```

**CAS Blob Tracking**
```java
// Pattern from content addressable storage
- SET operations for blob location tracking
- GET operations for blob availability checks
- SETNX for atomic blob placement
- Batch operations for multi-blob queries
```

### 2.4 Benchmark Scenarios

#### Scenario 1: Baseline Performance
**Objective**: Establish baseline metrics under typical load

**Configuration**:
- 1000 concurrent build operations/minute
- 50 active workers
- 80/20 read/write ratio
- Standard Buildfarm operation sizes

**Key Metrics**:
- Throughput (ops/sec)
- Latency (p50, p95, p99)
- Memory utilization
- CPU utilization
- Network bandwidth

#### Scenario 2: High-Throughput Build Bursts
**Objective**: Test performance under CI/CD traffic spikes

**Configuration**:
- 10,000 concurrent operations/minute burst
- 200 active workers
- Large batch operations (MGET/MSET)
- Mixed workload (queue + cache + coordination)

#### Scenario 3: Memory Pressure Testing
**Objective**: Compare behavior under memory constraints

**Configuration**:
- Fill to 80% memory capacity
- Enable eviction policies
- Monitor cache hit ratios
- Test failover scenarios

#### Scenario 4: Network Saturation
**Objective**: Test I/O threading effectiveness

**Configuration**:
- High connection count (1000+ clients)
- Large payload operations
- Network bandwidth saturation
- Concurrent read/write operations

#### Scenario 5: Real-World Mixed Workload
**Objective**: Simulate actual Buildfarm deployment

**Configuration**:
- Realistic mix of all operation types
- Variable load patterns (peak/off-peak)
- Multiple queue priorities
- Long-running operations with timeouts

## 5. Risk Mitigation

### Technical Risks
- **Compatibility Issues**: Thoroughly test protocol compatibility before extensive benchmarking
- **Configuration Drift**: Implement automated configuration validation
- **Environment Variables**: Control for hardware, network, and OS differences
- **Workload Accuracy**: Validate against actual Buildfarm telemetry data

### Operational Risks
- **Resource Constraints**: Plan for adequate compute and network resources
- **Timeline Delays**: Build buffer time for unexpected technical challenges
- **Data Quality**: Implement multiple validation checkpoints for metrics collection
